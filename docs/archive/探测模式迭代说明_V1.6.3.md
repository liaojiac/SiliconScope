## 二、为什么是 `AutoOnFirstRun`

针对你此前担心的两个问题，这个默认值恰好都解决了：

| 担忧 | `AutoOnFirstRun` 的应对 |
|------|------------------------|
| "每次都跑探测浪费开销" | ✅ **只首次一次，之后复用缓存**，零打扰零开销 |
| "命名不匹配怎么办" | ✅ **失败/缺失时自动提示"点击重新探测"**，按需干预 |

即：**正常无感知，出问题时才打扰你**——这是 UX 上最优的平衡点。

## 三、三种模式

| 模式 | 行为 | 适用 |
|------|------|------|
| **`AutoOnFirstRun`（默认）** | 首次自动探测 → 缓存复用；失败/缺失提示手动重探 | 正式版 |
| `AlwaysAuto` | 每次启动都重探 | 调试 |
| `OffUntilError` | 默认关闭，仅出错触发 | 极简场景 |

## 四、核心原则（代码已落实）

> **探测永远"尽力而为"，宁可缺字段也不抛异常。**

- 必需字段（VCore / PackageTemp / AvgFreq）缺失 → `ShouldPromptUser = true`
- 每核字段缺失 → **不计入必需失败**，避免老平台误报
- `ProbeState` 持久化到 `sensor_cache.json`
- 核心层不耦合 UI：`ShouldPromptUser` 由 UI 层决定是否弹窗

## 六、真机测试时的行为（你届时看到的）

1. 首次运行 → 自动探测，映射写入 `sensor_cache.json`（无感知）
2. 若探测不完整 → UI 提示"部分传感器未识别，点击重新探测"
3. 调试时可临时切 `AlwaysAuto` 观察命名变化

**无需手动对照命名表、无需手动 dump。**
