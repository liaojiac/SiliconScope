## 二、已应用的修正

### ① 评分算法：V/F 线性折算（★ 最关键）

- 旧：`vEquiv = input.VCore`（完全不折算），隐含假设"质控通过 = 同一工作点" → 被真机推翻
- 新：`SpScaler.AnchorVoltage / CalcSpAnchored`
  ```
  V_anchor = V_meas + (slope/1000) × (AnchorFreq − F_meas)
  SP       = clip(100 + (VRef / V_anchor − 1) × 300, 0, 150)
  ```
- **线性（带截距），不是此前被废弃的等比乘法** —— 这是关键区别
- 真机双点验证（已固化为回归用例）：

  | 工作点 | 不折算 SP | 折算后 SP |
  |--------|----------|----------|
  | OCCT 4526MHz@0.975V | 129.2（大雕） | **95.2** |
  | CPU-Z 4896MHz@1.127V | 84.8（偏弱） | **95.1** |
  | 分差 | **44.4** | **0.08** ✅ |

  锚点电压 1.0873 vs 1.0876 V（差 0.3mV），证明两点确在同一物理 V/F 直线上。

### ② 参数校准（数值有出处）

| 参数 | 旧值 | 新值 | 依据 |
|------|------|------|------|
| VRef | 1.050（拍脑袋） | **1.070** | GamersNexus Blender 全核 VID ≈1.07V |
| 锚点 | 无 | **4800 MHz** | 全核 stress 典型 ≈4.8GHz |
| 斜率 | 无 | **0.41 mV/MHz** | 真机双点反推 0.411，落在 Zen4 公开区间 0.35–0.45 内 |

### ③ 通用性（三级兜底 + 透明标注）

- `BaselineResolver.Resolve()`：**型号精确 → 代际默认/规格推算 → 全局默认**，并记录每个参数来源
- `ZenProfile.DefaultSlope()`：Zen/+/2=0.30、Zen3=0.35、**Zen4=0.41**、Zen5=0.45、未知=0.40
- 锚点推算：`MaxBoost × 0.94`，取整到 25MHz
- `CalibrationLevel`：**Calibrated**（仅 7800X3D，置信度 0.6）/ **Estimated**（其余，置信度 0.4）
- `VfFit.Fit()`：最小二乘自标定，≥3 点、频率有方差才返回，附 R²（为"越用越准"留算法底座）
- 报告对 Estimated 型号加显著水印，声明"不可直接对标华硕，仅供同型号横向比较"

### ④ 采集层修正

| 项 | 旧 | 新 |
|----|----|----|
| 核心电压匹配 | 写死 `Core (SVI2 TFN)` | **弹性 `IsCoreVddcr`**：含 VDDCR/SVI2/SVI3/Core Voltage/CPU Core，**排除 SoC/Misc/LDO/SMU** |
| 满载判定基准 | `ReferenceFreqMHz`（基础频率） | **`FullLoadFreqMHz`（MaxBoost）** |
| 满载阈值 | 0.95 | **0.90**（门槛 5000→4500MHz，容纳 OCCT/AVX-512 重负载） |
| 多轮采样 | 单次 Update | 新增 `SampleRounds=5` / `SampleIntervalMs=150` 配置（电压/频率/温度取均值，每核 VID 取峰值） |
| 转换 | 无 | 新增 `HardwareFeatures.ToScoreInput()`（串起主链路） |

### ⑤ 报告层修正

- 柱状图：固定上界 1.20V → **本次 min/max 归一化**（最低满格、最高保底 6 格），核间差异可见
- 新增**物理事实标注**：每核 VID 仅为 CPPC 请求值，Zen3/4/5 统一供电，核间排名仅供参考，不声称能复刻华硕每核 SP

- 新增口径提示（VID vs VDDCR 约 ±10mV → SP ±3~5 分）

### ⑥ 工程结构修正（★ 报告未明说但本库确认存在）

## 四、诚实提示（务必知悉）

1. **C# 仍未真实编译**：本沙盒无 .NET SDK（`dotnet: command not found`），以上为 **Python 逻辑等价验证 + C# 静态结构校验**，非编译期验证。
   - 报告已证明：静态走查会发现不了编译错误。因此**你在 VS/`dotnet build` 时仍可能遇到编译错误**（如 record 成员、`ProjectReference` 路径、元组语法）。
   - 请把报错贴来，我据此修正。**"必须能编译"应作为每次改动的强制门禁。**

2. **修正清单中需真机/编译环境才能最终确认的部分**（本轮仅完成代码层）：
   - 多轮采样的**实际循环实现**（`RealCollector.Read()` 真实采集块仍需在真机启用；本轮只加了配置项与聚合约定）
   - **PawnIO 单文件发布问题**（报告 §4.1）：属发布配置（`--self-contained` 文件夹发布，**禁止 `--single-file`**），不在源码内，需你在发布时遵守
   - 报告 §2 提到的其余编译错误（using 缺失、Guid 格式、模式匹配变量等）：我本轮未逐一比对，因无法编译验证；若 Build 报错即属此类

3. **算法口径不确定性**：VRef 用公开评测 **VID 口径**，实测为 **VDDCR 口径**，约 ±10mV → SP ±3~5 分。离线绝对分天然带此误差，报告已如实标注。

4. **当前结论**：你这颗 7800X3D 折算后 **SP ≈ 95（普通/偏弱边界）**，不是早期误报的"123 大雕"。这个结论已固化进回归用例，防止算法回退。
