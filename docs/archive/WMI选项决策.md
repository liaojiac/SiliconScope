# WMI 选项决策记录

> 状态：**已决策 — 否决（采用方式 A：直接嵌入 LibreHardwareMonitorLib）**
> 决策人：产品负责人（用户）
> 日期：2026-09-18（V1.6.1）

## 背景

V1.6 兼容设计文档曾把"是否改用 LHM 的 WMI 接口"列为待确认项，理由是：
LHM 官方 `root/LibreHardwareMonitor` WMI 命名空间的传感器名由 LHM 统一、跨主板一致，
可简化兼容层的弹性匹配逻辑。代价是**依赖 LHM 的 WMI 数据采集进程在后台运行**。

## 澄清："依赖后台服务"对用户意味着什么

经明确澄清，两种集成方式有本质区别：

| 方式 | 集成对象 | 用户需自行安装/运行 LHM？ | 后台进程 |
|------|---------|--------------------------|---------|
| **A. 直接嵌入（当前方案）** | `LibreHardwareMonitorLib` NuGet 包编译进本软件 | ❌ 不需要 | 无 |
| **B1. WMI + 独立 LHM** | 读 LHM 的 WMI 命名空间 | ⚠️ 需要用户装并运行 LHM | 有（LHM 进程）|
| **B2. WMI + 自带采集进程** | 随软件自启一个精简采集进程注册 WMI | ❌ 不需要 | 有（自启进程，需维护生命周期）|

**关键**：`LibreHardwareMonitorLib`（开源库 DLL）≠ `LibreHardwareMonitor`（独立 GUI 程序）。
当前 V1.6 用的是方式 A，把 DLL 直接编译进软件，**不产生任何后台服务**。

## 决策理由（为何否决 WMI / 方式 B）

V1.6 的四层兼容防御（弹性匹配 + 合理性校验 + 探测自省 + 指纹缓存/众包）
**已经解决了跨主板命名稳定性问题**，因此：

1. ✅ **方式 A → 用户零负担**：不用装、不用开 LHM，无后台服务 ← **体验最优**
2. ✅ **兼容层已覆盖命名差异**：WMI 的核心卖点（命名统一）**不再构成优势**
3. ✅ **无后台进程 / 无权限 / 无生命周期管理负担**：打包、沙盒、部署都更简单
4. ❌ **方式 B 的代价（后台进程 + 权限 + 自启维护）是实打实的**，而收益已被兼容层抵消
   → **得不偿失，否决**

## 结论

- **最终方案：方式 A（直接嵌入 `LibreHardwareMonitorLib` NuGet 包）**
- **用户无需安装、无需运行任何 LHM 程序，也无需任何后台服务**
- 兼容层维持现状（V1.6 四层防御），不再评估切换到 WMI
- **本决策项从「待确认」正式关闭**，相关文档已同步更新：
  - `LHM跨主板兼容设计.md` §四（划除 WMI 段落，标注已决策）
  - `LHM跨主板兼容设计.md` §七（移除"是否改用 WMI"待确认项）

## 复现/回滚条件

仅在以下情况发生时重新评估本决策：
- LHM 官方**停止维护/弃用**直接嵌入的 Lib，或
- 出现**仅靠命名兼容层无法解决的、普遍存在的采集失败**（届时优先考虑扩展兼容层，而非切 WMI）
