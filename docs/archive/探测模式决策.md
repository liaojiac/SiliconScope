# 探测模式决策记录

> 状态：**已决策 — `AutoOnFirstRun`（首次自动探测 + 出错提示手动重探）**
> 决策人：产品负责人（用户）
> 日期：2026-09-18（V1.6.3）
> 对应：LHM跨主板兼容设计.md §七〔待确认〕第 3 项

## 背景

V1.6 兼容层引入了"探测模式"概念（首次/未命中时自动 dump 传感器 + 按规则自动匹配 + 建缓存），
但**探测的"默认行为"一直未定**：是每次都探、首次探一次、还是默认关闭仅在出错时探？
这直接影响用户体验（打扰频率）与性能（探测开销）。

## 决策结论

**默认采用 `AutoOnFirstRun`**：首次运行自动探测一次 → 映射写 `sensor_cache.json` → 后续启动直接复用缓存（零打扰、零开销）；**仅当探测失败 / 必需字段缺失时才弹出提示，引导用户"点击重新探测"**。

## 三种模式对比

| 模式 | 行为 | 适用 |
|------|------|------|
| **`AutoOnFirstRun`（默认）** | 首次自动探测一次 → 缓存复用；失败/缺失时提示手动重探 | **正式版** |
| `AlwaysAuto` | 每次启动都重探 | 调试 / 传感器命名频繁变化 |
| `OffUntilError` | 默认关闭探测，仅出错/字段缺失时提示手动触发 | 极简场景 |

## 理由

1. ✅ **正常情况用户零感知**：首次探测一次即缓存复用，不会"每次都跑探测"浪费开销（解决你担心的性能问题）
2. ✅ **只有真正出问题时才打扰用户**：探测失败/字段缺失才弹提示，符合"按需干预"原则
3. ✅ **与手册 §5 自检清单一致**：探测是自动适配的，无需用户手动对照命名表
4. ✅ **核心层不耦合 UI**：是否弹窗由 `ShouldPromptUser` 决定，UI 层负责展示，可跨 WinForms/WPF/CLI 复用
5. ✅ **退化安全**：探测失败也只是"字段缺失 → 拒评"，不会评出假分（合理性校验仍是最后防线）

## 关键设计原则（代码落实）

> **探测永远"尽力而为"，宁可缺字段也不抛异常。**

- 必需字段（VCore / PackageTemp / AvgFreq）缺失 → `ShouldPromptUser = true`
- 每核字段（VID / 有效频率）缺失 → **不计入必需失败**，避免无每核数据的老平台误报
- `ProbeState` 持久化到 `sensor_cache.json`：`HasEverProbed` / `LastProbedAt` / `FailureCount` / `MissingFields`
- `Advance()` 成功重置失败计数、失败累计失败次数，供 UI 判断"是否需要引导"

## 真机对接要点

你在真机测试时只需：

1. 首次运行 → 程序自动探测，映射写入 `sensor_cache.json`（无感知）
2. 若探测不完整 → UI 提示"部分传感器未识别，点击重新探测"
3. 调试时可临时切 `AlwaysAuto` 观察每次命名变化

**无需手动对照命名表、无需手动 dump**——这正是探测模式的价值。

## 复现/重新评估条件

若出现"首次探测结果不稳定 / 缓存失效频繁"等实际问题，再考虑：
- 丰富候选列表（弹性匹配第 ① 层）
- 引入 LHM WMI 的稳定命名（此前已否决，需重新评估）
