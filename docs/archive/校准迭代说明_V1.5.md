> 本轮：对 `Collector.cs` / `Collector.Real.cs` 的 LHM 传感器关键词做**真实命名校准**
> 触发：上一轮代码中关键词为经验性写法，本轮核对 LHM 源码 `Amd17Cpu.cs` 后确认存在错误
> 验证：`采集层/verify_naming.py`（10/10）+ 全量回归 4/4

## 一、★ 校准中暴露的真实 Bug（已修复）

校准**不是空跑一遍**，而是立刻抓出了两个会在真机上**静默出错**的问题：

### Bug 1：VCore 会误采 SoC 电压（致命）

**代码**：`sensor.Name.Contains("SVI2 TFN")` → VCore

**问题**：`"SoC (SVI2 TFN)"` 也 Contains `"SVI2 TFN"`，会被当成 VCore。
→ 体质评分用了 SoC 电压（约 1.05V，普遍偏高），**全体 CPU 被评成"雷"或"偏弱"**，且是静默错误，不报错。

**修复**：改为**精确匹配** `s.Name == "Core (SVI2 TFN)"`。
验证：`verify_naming.py` 中 SoC 正确被忽略。

### Bug 2：正则括号未转义 → 每核数据全部漏采

**代码**：`new Regex(@"^Core #\d+ (Effective)$")`

**问题**：`(Effective)` 中的 `()` 被当成正则**捕获分组**，导致 `"Core #0 (Effective)"` **匹配失败**。
→ 每核 VID / 有效频率 / 瞬时频率**全部采不到**（`PerCoreVIDs` 为空），核心体质分布功能报废。

**修复**：转义为 `\(Effective\)`。同理 `^Core #\d+$` 无括号无需转义。
验证：`verify_naming.py` 中 8 核数据全部正确采集。

> **教训**：这类正则 bug 在 C# 里编译不报错、运行不报错，只有真机发现"每核数据全空"。
> 校准的价值就在于**用命名验证脚本把它提前暴露**。

## 二、关键认知更正

| 旧认知（手册写的） | 校准后（源码确认） |
|-------------------|------------------|
| LHM 读不到每核 VID，靠 HWiNFO | **LHM 原生支持** `Core #N VID` |
| 有效频率靠 HWiNFO | **LHM 有** `Core #N (Effective)`（APERF/MPERF）|
| CCD 温度靠 HWiNFO | **LHM 有** `CCDx (Tdie)` |
| HWiNFO 是必需增强 | **降级为可选冗余校验** |

→ **HWiNFO SHM 的角色被大幅弱化**：双源架构（LHM + HWiNFO）仍可保留，但**LHM 单源即可覆盖体质评分全部必需字段**。
→ 这也意味着：用户**不装 HWiNFO 也能完整评分**，符合你最初"尽量减少依赖"的诉求。

## 三、新增：双源交叉校验（防假大雕加固）

既然 LHM 同时提供 **SVI2 遥测（Core SVI2 TFN）** 和 **VRM 读数（CPU VCore）**，两者应一致：

```csharp
if (Math.Abs(svi2 - vrm) > 0.05) → 拒绝评分
```

比单靠 `QualityGate` 的电压范围校验**多一道独立防线**。已写入手册 Step 4.2 与 `Collector.Real.cs`。

## 六、诚实提示

1. **命名校准基于 LHM 开源源码 + 文档**，未在你真机上实测——不同主板/BIOS 的传感器命名可能有细微差异。
   **真机首次运行时务必按手册 §5 自检清单逐项核对**，尤其是 VCore 是否精确匹配 `Core (SVI2 TFN)`。
2. **正则转义已修正，但 C# 代码仍为注释状态**（骨架未启用 LHM 真实调用），待你在 Windows 启用。
3. CCD 温度命名在 Zen/Zen+ vs Zen2+ 有差异，手册已注明兼容写法。
