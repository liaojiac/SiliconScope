## 二、用户的两个决策（已落地）

| 决策点 | 选择 | 落地位置 |
|--------|------|----------|
| **Q1：日志文件放哪？** | **A：程序同级 `logs/` 目录** | `Logger.Configure()` |
| **Q2：诊断报告是否自动生成？** | **A：每次采集自动生成，保留最近 10 份** | `DiagnosticStore.RetainCount = 10` |

推导出的设计原则（贯穿三层）：
- **便携优先**：相对路径，兼容 U 盘 / 免安装场景（不用 `%LocalAppData%`）
- **自动但克制**：自动生成 + 保留上限（防磁盘膨胀）
- **过程 ≠ 成品解耦**：日志（过程流水）、诊断报告（单次快照）、导出（给用户看的成品）三者职责分离

## 三、三层设计

### ① Logger.cs（采集层，结构化日志）

- **每条日志** = 时间戳(Utc) + 级别 + 消息 + 上下文(Context, dict) + 异常
- **级别**：`Verbose(0) / Info(1) / Warn(2) / Error(3)`，默认 `MinLevel=Info`（Release 可关 Verbose）
- **双输出**：Console（实时）+ 滚动文件（按天 `yyyyMMdd.log`，跨天自动切分，无需外部定时器）
- **进程级单例** `Logger.Instance`，任意模块可写
- **线程安全**：lock 串行化写盘
- **护栏**：写盘失败**绝不抛异常**，仅回退控制台——日志是排查辅助，不能拖累主流程
- **关键修正**：`Error(msg, exception, context)` 参数顺序统一为 `(level, msg, ctx, ex)`，避免把异常当上下文（这是早期验证脚本踩过的坑）

用法：
```csharp
Logger.Instance.Info("采集开始", new { model = "7800X3D" });
Logger.Instance.Warn("字段缺失", new { missing = new[] { "VCore" } });
Logger.Instance.Error("采集失败", ex, new { source = "LHM" });
```

### ② Diagnostic.cs（采集层，单次采集快照）

一份诊断报告 = 排查所需的**一切**，可脱离程序独立分析：

```
DiagnosticReport
├─ 元信息：ReportId / GeneratedAt / AppVersion
├─ Environment：管理员 / 核心隔离 / OS / .NET / LHM 可用性
├─ SensorDump[]        ★ 全部原始传感器 (hw/type/name/value)
├─ FieldResolution[]   逻辑字段 → 实际原始名 → 采样值 → 是否命中 → 匹配规则
├─ MissingFields[]     未命中的逻辑字段（自动推导，单一来源）
├─ Validation          { EnvironmentOk, RationalityOk, FullLoadOk, QualityGateOk, RejectReason }
├─ Score               { Mode, SpScore, Percentile, Grade, Confidence, Best/WorstCore }
└─ Errors[]
```

**落盘策略**：
- `DiagnosticStore.Save()` → `reports/diagnostic_yyyyMMdd_HHmmss_<id前6位>.json`
- `RetainLatest(keep=10)` → 自动清理旧文件（占用中跳过，下次再试）
- **`finally` 语义**：采集无论成败都落盘（失败时的传感器 dump 最珍贵）

**一键打包 `PackDiagnosticBundle()`**：
```
诊断包_时间戳/
├─ logs/               运行日志（按天切分）
├─ reports/            单次采集诊断报告
├─ sensor_cache.json   传感器映射缓存 + 探测状态
└─ README.txt          人类可读入口说明
```
→ 打包为 `诊断包_时间戳.zip`。**出问题时把整个 zip 发来即可定位，无需复现。**

### ③ Exporter.cs（评分引擎，评分解导出）

- **JSON**（`ToJson`）：供程序回读 / 云端上报预留，字段稳定、camelCase、顺序固定（利于 diff）
- **Markdown**（`ToMarkdown`）：供人阅读 / 论坛分享，含核心体质分布字符柱状图（█，VID 越低越长）
- **`ExportBoth()`**：同时出 JSON + MD，一份给程序一份给人，避免两份数据不同步
- 导出内容与渲染分离（只生成 Markdown，是否转 HTML/PDF 由上层决定，避免核心逻辑依赖渲染库）

## 四、本轮修正的真实问题

### 问题 A：`run_all_tests.py` 汇总误判（回归入口 bug）

**症状**：每个子脚本内部全 ✅，但汇总全显示 `FAIL(exit)`。

**根因**：原脚本用 `exec` 执行子脚本，捕获 `SystemExit` 时把 `sys.exit(0)`（成功透传）
一律当成失败；且 `PASS/FAIL` 是子脚本局部变量，`exec` 后作用域取不到 → 计数恒为 0。

**修复**：改为**子进程运行 + 解析 stdout 汇总行**（单一来源，最不易失同步）。
为兼容仓库内三种汇总格式，引入多正则解析：

| 格式 | 示例 | 来源脚本 |
|------|------|----------|
| `N passed, M failed` | `29 passed, 0 failed` | logging / structure / probe_mode |
| `结果：N passed, M failed` | `结果：15 passed, 0 failed` | naming / compat / scoring |
| `结果：N/T passed` | `结果：14/14 passed` | compat（分数形式） |

### 问题 B：stdout 缓冲导致结构校验输出丢失

**症状**：`verify_structure.py` 直接跑无输出，subprocess 捕获 stdout 为空，但 `rc=0`。

**根因**：脚本末尾用 `os._exit(0)` 立即终止进程，未 flush stdout 缓冲区；
管道/文件捕获场景下缓冲区来不及写出（终端交互模式因行缓冲正常，管道模式失效）。

**修复**：
- 汇总脚本子进程统一加 `python -u` + 环境变量 `PYTHONUNBUFFERED=1`
- **不影响你真机**：Windows 上通过 `dotnet` 直接运行，不存在此问题；这是沙盒 Python 验证层的事项

### 问题 C：子脚本汇总格式不统一

**修复**：在 `run_all_tests.py` 的解析器里兼容三种格式（见上表），
后续新增脚本**只需用以上任意一种格式打印末尾汇总**，即可自动接入回归。

## 七、诚实提示（务必知悉）

1. **C# 代码未经 dotnet 真实编译**：沙盒为 Linux 且无 .NET SDK，
   以上全部为 **Python 逻辑等价验证 + C# 静态结构校验**，非编译期验证。
   **Windows 首次 `dotnet build` 可能因 record 语法/命名空间微调 1-2 处**——这是预期内，
   届时把报错贴来远程协助。

2. **`DiagnosticReport` 的无参构造器 `: this(...)` 链式调用**：
   在 .NET 8 下有效，但若用更早版本需确认 record 无参构造器支持。

3. **日志/报告默认写入程序同级目录**（`AppContext.BaseDirectory/logs`、`/reports`）：
   若以管理员权限安装到 `Program Files`，写入可能受 UAC 限制——
   建议便携部署，或由启动器确保目录可写（后续可在 `CollectorOptions` 里覆盖路径）。

4. **V_ref 仍为估算值**，绝对 SP 标注"仅供参考"真实必要，导出报告也会如实注明。

## 八、真机使用流程（给你后续测试用）

```
1. 解压 → dotnet build
2. 首次运行 → 自动探测传感器映射 → 写入 sensor_cache.json（无感知）
3. 正常采集 → logs/ 追加日志，reports/ 存诊断报告（保留最近 10 份）
4. 出问题时 → 程序菜单「导出诊断包」→ 生成 诊断包_时间戳.zip
5. 把 zip 发来 → 基于 SensorDump + FieldResolution 定位命名/匹配/质控问题
```

无需手动对照命名表、无需手动 dump——这正是探测模式 + 日志体系的价值闭环。
