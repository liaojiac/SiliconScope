## 🔧 本轮捕获并修复的 3 个真实 Bug

> 这些都是**不跑数据流就不会发现**的问题，说明验收脚本的价值。

### Bug 1：SP 单调性断言硬编码阈值（测试本身有 bug）
- **现象**：`1.12V 期望 82.1` 但实际 81.2，测试误报失败
- **根因**：测试把动态计算值 `100+(1.05/1.12-1)*300` 硬编码成 82.1
- **修复**：改为动态计算期望值
- **教训**：**测试的期望值得来自同一公式，不能手填**

### Bug 2：跨 Zen 归一化失真（设计缺陷）
- **现象**：同电压 1.05V 下 Zen3 vs Zen4 的 SP 差 20 分
- **根因**：量表 V_ref 差异（1.12/1.05）被 Scale=300 放大
- **修复 + 认知升级**：**华硕 SP 本就是型号相关的绝对分**，跨代可比性应由**云端分位表（每型号独立 μ/σ）**保证，而非强行统一 V_ref
- **文档**：详见《频率折算勘误.md》

### Bug 3：频率折算导致正常电压被算成"大雕"（设计缺陷，最严重）
- **现象**：5GHz@1.02V → V_equiv=0.857 → SP≈267 → clip 150 → 误判大雕
- **根因**：把"采集电压"再折算回额定频率，重复折算
- **修复**：**评分一律用实测稳态电压，频率仅用于满载质控**（F_meas ≥ 额定×95%）
- **影响**：这是防"假大雕"的第二道闸门，已在勘误中固化

## ⚠️ 关键设计决策（已固化）

> 来自《频率折算勘误.md》，需同步更新到算法文档 §4.2：

```
SP = 100 + (V_ref / V_meas − 1) × Scale       # 仅用实测电压
F_meas 用途：质控（是否满载），不参与公式
跨代可比：云端分位表（型号独立 μ/σ），非频率折算
```

## 📌 诚实提示（必须让你知道）

1. **当前评分引擎与采集层均为骨架/原型级**
   - C# `Collector.Collect()` **返回 null**——真实 LHM 读取需在 Windows + AMD 硬件上补全
   - Python 验收用的是**模拟数据**，证明的是"算法与流程正确"，**不是真实硬件读数**

2. **V_ref 仍是估算值**（`spec_reversal`）
   - 绝对 SP 标注"仅供参考"是**真实必要的**
   - 校准依赖云端样本库积累（目标 ρ≥0.90）

3. **云端服务本轮仍未实现**（按你的决策放后续迭代）
   - 当前"在线模式"用的是**硬编码的模拟分位表**（`CLOUD` dict）
   - 真实云端对接时，只需替换 `ICloudStats` 实现，**接口已预留无需改结构**

4. **C# 单测代码写好了，但未在 .NET 上实际跑过**
   - 沙盒是 Linux，无法 `dotnet test`
   - Python 验收与 C# 算法**逻辑对齐**，但**首次在 Windows 编译时可能需微调**（如 record 模式匹配语法）
