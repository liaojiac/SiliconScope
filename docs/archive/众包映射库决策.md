# 众包映射库决策记录

> 状态：**已决策 — 不做（首版 + 可预见阶段仅本地缓存）**
> 决策人：产品负责人（用户）
> 日期：2026-09-18（V1.6.2）

## 背景

V1.6 兼容设计文档曾把"是否做众包映射库"列为待确认项。动机是：
跨主板/BIOS 的传感器命名差异，理论上可通过**收集大量真实设备的映射**来规模化覆盖长尾主板，
比"单机探测 + 内置候选列表"更彻底。

## 决策结论

**不做众包映射库。** 首版及可预见阶段均**仅保留本地缓存**，`BoardCache` 只在本机复用映射。

## 理由

1. ✅ **当前场景不需要**：单机自用 + 小范围测试，"同主板免重复探测"靠本地缓存已足够
2. ✅ **彻底规避隐私/合规风险**：映射数据虽不含敏感信息，但不上传即无数据合规负担
3. ✅ **省掉后端维护成本**：无采集服务、无存储、无版本管理、无反作弊
4. ✅ **长尾主板有兜底**：第 ①②③ 层（弹性匹配 + 合理性校验 + 探测自省）不依赖群体数据
5. ✅ **未知主板自愈**：本地缓存覆盖不到时，`SensorProbe` 自动探测一次并建映射，对单用户透明

## 与 WMI 决策的一致性

此前已否决 WMI 选项（方式 A：直接嵌入，无后台服务）。
本次"不做众包"延续同一原则：

> **能不引入服务端就不引入，能单机闭环就单机闭环。**

两者叠加后，**本软件的采集层完全本地化，零服务端依赖**——
这与你此前"云端排行榜只留接口、后续迭代"的整体架构取向一致。

## 对现有代码的影响

- `BoardCache`：**保持现状**，仅本机 JSON 缓存，不做上报
- `SensorProbe`：**保持现状**，探测结果只写本地 `sensor_cache.json`
- **不新增**任何上报/同步逻辑、`/api/mapping` 之类接口
- 数据库详细设计中若涉及"映射上报"相关表/接口 → **同步移除或标注为不适用**

## 复现/重新评估条件

仅在以下情况发生时重新考虑本决策：

- 出现**大量、普遍、单机探测无法覆盖**的命名变体（如某厂商 BIOS 大规模改命名）
- 明确的**跨用户规模化机型覆盖**刚需（产品定位从"单机工具"转向"平台型产品"）

届时**优先考虑扩展兼容层（丰富候选列表 + 规则引擎），而非直接补众包**。
